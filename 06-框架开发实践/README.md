# 第六章　框架开发实践

> 第四章手写范式、第五章用低代码平台，这一章走第三条路：**用业界框架写代码**。既要框架带来的复用、解耦、可观测，又要保留代码的控制力和可扩展性。
>
> 说明：教材示例代码在官方 `code` 目录中，本仓库未放置。

## 0. 一句话记住四个框架

| 框架 | 核心比喻 | 设计哲学 | 最适合 |
|---|---|---|---|
| **AutoGen** | 圆桌会议 | 对话驱动协作 | 角色分工明确的流程化任务 |
| **AgentScope** | 智能体操作系统 | 消息驱动 + 工程化 | 高并发、分布式、生产级系统 |
| **CAMEL** | 两位专家对谈 | 角色扮演 + 引导性提示 | 双智能体深度协作、创造性任务 |
| **LangGraph** | 流程图/状态机 | 图 + 显式控制 | 可审计、可回滚的生产工作流 |

---

## 1. 为什么从手写走向框架（6.1）

| 价值 | 说明 |
|---|---|
| **代码复用** | 框架封装了 Agent Loop，ReAct / Plan-and-Solve 都能用标准组件快速搭 |
| **分层解耦** | 模型层 / 工具层 / 记忆层分开，换模型、加工具互不影响 |
| **状态管理** | 上下文窗口、历史持久化、多轮状态跟踪，不用自己造轮子 |
| **可观测性** | 生命周期回调（`on_llm_start`、`on_tool_end` 等）自动打点，比到处 `print` 强得多 |

> 一句话：**框架把「所有智能体都一样」的部分封起来，让你只写「这一个智能体不一样」的部分。**

## 2. 框架一：AutoGen（6.2）

**机制**：把多智能体协作抽象成「群聊」。每个 Agent 是群聊成员，按规则轮流发言，任务在对话中推进。

教材以 0.7.4 为例，重点讲了三件事：
- **分层架构**：`autogen-core`（底层消息/模型）+ `autogen-agentchat`（上层对话 API）
- **异步优先**：全面 `async/await`，等待 LLM 时不阻塞其他 Agent
- **核心角色**：`AssistantAgent`（思考）+ `UserProxyAgent`（代表人类发起任务、执行代码）

**案例：模拟软件开发团队**
- 四个角色：产品经理 → 工程师 → 代码审查员 → 用户代理
- `RoundRobinGroupChat` 按顺序轮询发言
- `TextMentionTermination("TERMINATE")` + `max_turns=20` 双重终止，防死循环

**优势**：对话即流程，建模门槛低；角色通过 System Message 高度专业化、可复用；`UserProxyAgent` 天然支持 Human-in-the-loop。

**局限**：对话有不确定性，可能跑偏或循环；出错时只有一长串对话历史，**对话式调试**很痛苦。

---

## 3. 框架二：AgentScope（6.3）

**机制**：消息驱动架构。所有交互都是 `Msg` 的发送/接收，而不是函数调用；消息中心 `MsgHub` 负责路由、广播、持久化和跨节点通信。

四层结构：
- 基础组件（Message / Memory / Model / Tool）
- 智能体基础设施（预置 Agent、ReAct、钩子、并行工具调用）
- 多智能体协作（`MsgHub` + `Pipeline`：顺序 / 并发）
- 开发与部署（AgentScope Runtime + Studio）

**案例：三国狼人杀**
- 用 `MsgHub` 动态开「狼人私聊频道」，用 `fanout_pipeline` 并行收集投票
- 用 Pydantic 结构化输出（`DiscussionModelCN`、`WitchActionModelCN`）把游戏规则变成代码约束
- 双重角色建模：游戏角色（狼人/预言家）+ 人物性格（曹操/张飞）

**优势**：异步解耦、位置透明、消息可持久化可重放；原生分布式部署；单点异常有容错兜底。

**局限**：概念多、门槛高，简单场景容易**过度工程化**；生态相对年轻。

## 4. 框架三：CAMEL（6.4）

**机制**：双智能体角色扮演。一个当 `AI User`（提需求、拆步骤），一个当 `AI Assistant`（执行、给方案），靠 **Inception Prompting**（引导性提示）把双方「锁」在角色里。

引导性提示的四要素：明确自身角色 → 告知协作方角色 → 定义共同目标 → 设定行为约束与完成标志（如 `<CAMEL_TASK_DONE>`）。

**案例：AI 科普电子书**
- 心理学家（assistant，提供专业知识）+ 作家（user，负责结构与表达）
- `RolePlaying(...)` 一行配置角色，`init_chat()` 开场，`step()` 驱动一问一答
- 30 轮上限；协作自然分成「搭框架 → 内容生成 → 迭代打磨 → 收尾」四阶段

**优势**：「轻架构、重提示」，代码极少；协作行为从提示中「涌现」，灵活；现已扩展多模态、工具库、多模型，并支持与 LangChain / CrewAI / AutoGen 互操作。

**局限**：高度依赖提示质量，效果不好时很难定位是角色、任务还是规则的问题；大规模多智能体场景缺少路由、状态同步和冲突仲裁。

## 5. 框架四：LangGraph（6.5）

**机制**：把智能体流程建模为**有向图状态机**——三个要素：

| 要素 | 含义 |
|---|---|
| **State** | 全局共享状态（通常 `TypedDict`），所有节点可读可写 |
| **Node** | 一个 Python 函数，接收状态、返回状态增量 |
| **Edge** | 普通边（固定跳转）+ 条件边（根据状态动态路由，实现循环和分支） |

**案例：三步问答助手**
`understand`（理解意图 + 生成搜索词）→ `search`（Tavily 真实搜索，失败则记录 `search_failed`）→ `answer`（成功用搜索结果答，失败回退到模型自身知识）。
加 `InMemorySaver` 作为 checkpointer，即可多轮对话、断点续跑。

**优势**：流程显式、高度可控可审计；**原生支持循环**，反思-修正、生成-测试-修复都很自然；节点即函数，模块化强；插入人工审核节点很方便。

**局限**：样板代码多，简单任务显得繁琐；行为可预测但不「涌现」，不适合开放式社会性协作；调试要同时看节点逻辑、状态变化和边条件。

## 6. 本章真正的重点：两组权衡（6.6）

**① 涌现式协作 vs 显式控制**
- AutoGen / CAMEL：只定义「谁」和「要什么」，流程从对话中自然长出来 → 灵活、像人，但难预测、难调试。
- LangGraph：把每一步和跳转条件都写死 → 可靠、可审计，但牺牲灵活性和「惊喜」。

**② 能跑 vs 能稳定服务**
AgentScope 提醒我们：无论选哪种协作范式，要上生产都要面对并发、容错、分布式部署、可观测性。这是「原型」和「产品」之间的鸿沟。

## 7. 教材之外的 2026 框架格局（重要更新）

教材写于 2025 年上半年，此后框架生态发生了**代际更替**。以下是截至 2026 年 11 月的主流格局。

### 7.1 教材里四个框架的现状

| 框架 | 现状 |
|---|---|
| **AutoGen** | ⚠️ 已进入**维护模式**。微软把 AutoGen 的编排能力与 Semantic Kernel 的企业级基础合并为 **Microsoft Agent Framework**，官方提供迁移指南。新项目不建议再基于 AutoGen 起步 |
| **AgentScope** | ✅ 仍在快速演进。2025 年 10 月发布 **1.0**（核心框架 + Runtime + Studio 三层），PyPI 已到 2.x；2025 年 12 月还发布了 **AgentScope Java 1.0** |
| **CAMEL** | ✅ 活跃。已从双智能体扩展到 `workforce` 多智能体、多模态、工具库，并支持与其他框架互操作 |
| **LangGraph** | ✅ **1.0 于 2025-10-22 GA**，是首个稳定大版本；当前 1.2.x，配套 LangChain 1.0 |

### 7.2 新晋主流框架

| 框架 | 出身 | 核心特点 | 适合谁 |
|---|---|---|---|
| **Microsoft Agent Framework** | 微软 | 1.0 GA（2026-04），AutoGen + Semantic Kernel 的正统继任者；Python / .NET，Go 预览；图式工作流、企业级可观测 | .NET / Azure 技术栈、原 AutoGen/SK 用户 |
| **OpenAI Agents SDK** | OpenAI | 轻量 Agent Loop + Handoffs + Guardrails + Tracing；Swarm 的生产版 | 想快速上手、不想要重框架 |
| **Claude Agent SDK** | Anthropic | 由 Claude Code SDK 更名而来；内置文件/命令/搜索工具、Hooks、Subagents、MCP | 做「会动手干活」的编码/自动化 Agent |
| **Google ADK** | Google | Python 1.0 → **2.0 GA（2026-05）**，TypeScript 2.0（2026-08），Java / Go 1.0；与 Gemini、A2A 深度绑定 | GCP / Gemini 生态、多智能体 |
| **CrewAI** | CrewAI | 角色化 Crews + Flows；上手快、社区大，强调「像带团队一样配 Agent」 | 快速搭业务流程、原型验证 |
| **PydanticAI** | Pydantic 团队 | 类型安全、结构化输出、依赖注入，FastAPI 式的开发体验 | 重视类型与可测试性的 Python 团队 |
| **Strands Agents** | AWS | 模型驱动（model-driven）的轻量 Agent SDK，默认接 Bedrock | AWS 技术栈 |

### 7.3 给 Java 开发者的补充（教材没讲，但对你最实用）

| 框架 | 定位 |
|---|---|
| **Spring AI** | Spring 官方，`ChatClient` + Advisor + 工具调用 + RAG，Spring Boot 项目接入成本最低；1.0 已 GA，2.0 面向 Spring Boot 4 |
| **LangChain4j** | Java 版 LangChain，`AiServices` 声明式接口、向量库兼容最广；Quarkus / 普通 Java 也能用 |
| **AgentScope Java 1.0** | 阿里通义实验室，把 AgentScope 的消息驱动、多智能体能力带到 Java，适合企业级高并发 |
| **Embabel** | Spring 创始人 Rod Johnson 的 Agent 框架，主打「目标导向 + 领域模型」，要求 JDK 21 |

> 选型经验：**已有 Spring Boot 体系 → Spring AI；需要多模型/多向量库/非 Spring → LangChain4j；要分布式多智能体 → AgentScope Java。**

### 7.4 三个明显趋势

1. **从「编排框架」转向「Agent Harness + Runtime + 沙箱」**：Claude Agent SDK、OpenAI Agents SDK、Strands 都在强调「给模型一套能动手的工具和安全运行环境」，而不只是串流程。
2. **MCP 成为工具接入事实标准，A2A 成为智能体间通信标准**：工具和 Agent 都变成可插拔协议，框架之间的壁垒在降低。
3. **「图/工作流」成为生产共识**：LangGraph、ADK 2.0、Microsoft Agent Framework、CrewAI Flows 都在往显式工作流 + 持久化执行靠拢；纯对话式编排更多用于原型。

## 8. 怎么选（结合教材 + 2026 现状）

| 你的场景 | 推荐 |
|---|---|
| 学习原理、理解编排范式 | 教材四框架仍值得读，尤其 LangGraph 和 AutoGen |
| 新项目、Python、要上生产 | **LangGraph 1.x**（可控可审计）或 **Microsoft Agent Framework**（微软栈） |
| 多智能体、要分布式/高并发 | **AgentScope 1.0+** |
| 轻量、快速验证、工具调用为主 | **OpenAI Agents SDK** / **PydanticAI** / **CrewAI** |
| 编码类、需要真实操作文件与命令 | **Claude Agent SDK** |
| Google Cloud / Gemini | **Google ADK 2.0** |
| Java / Spring 体系 | **Spring AI** 或 **LangChain4j**，分布式选 **AgentScope Java** |

## 附录：大白话理解第六章

> 第六章就一句话：**你已经会自己做饭了（第四章），也逛过预制菜超市（第五章），现在学的是「买一套趁手的厨房设备」——效率更高，但菜还是你自己炒。**

### 四个框架，四种「带队方式」

| 框架 | 生活类比 | 特点 |
|---|---|---|
| AutoGen | 开圆桌会：产品、开发、测试轮流发言 | 谁都能说话，流程靠对话推进，热闹但容易跑题 |
| AgentScope | 正规公司：有工位、有内线电话、有值班表 | 消息统一走「总机」，谁在哪台机器上都无所谓，稳定但规矩多 |
| CAMEL | 两个人搭档：一个出主意，一个动手做 | 写好「合作说明书」就能自动配合，人少效率高 |
| LangGraph | 流程图贴在墙上：每一步做什么、什么情况回头重做，写得明明白白 | 最可控、最不容易出岔子，但前期画图费劲 |

### 「涌现」和「显式」到底差在哪？
- **涌现** = 你只告诉团队「把这事做成」，他们自己商量着办。像放养，可能给你惊喜，也可能跑偏。
- **显式** = 你把每一步都写成 SOP，谁在第几步做什么、什么条件退回上一步。像流水线，稳定但死板。

做玩具可以放养，做银行系统必须 SOP。

### 为什么教材刚写完，框架就「换代」了？
因为这个领域半年就是一代。教材里的 AutoGen 已经被微软合并进新框架了，LangGraph 已经出了 1.0 稳定版，Google ADK 都到 2.0 了。

**但别慌**：变的是 API 名字，不变的是那四种思路——对话协作、消息驱动、角色扮演、图状态机。你理解了这四种思路，换任何框架都是查文档的事。

### 给 Java 开发者的一句话
> 不用羡慕 Python。Java 这边 Spring AI、LangChain4j、AgentScope Java 都能打，甚至因为企业级工程能力（事务、监控、部署）更成熟，做生产系统反而更稳。

### 一句话记全章
> **手写懂原理，平台出原型，框架做生产；选框架看两件事——你要「涌现」还是「可控」，以及你能不能扛住工程化。**
