# 第九章　上下文工程

> 第八章解决了"记得住、查得到"，但还有个更根本的问题：**每次调模型时，到底该往上下文窗口里塞什么？** 塞少了模型缺信息，塞多了模型"走神"。这一章就是把这件"凭手感"的事变成一套可复用、可度量、可演进的工程流程。
>
> 框架版本：`pip install "hello-agents[all]==0.2.8"`，需要 `.env` 里配好 LLM API（本章主要靠 LLM 做上下文管理与决策）。

---

## 0. 一句话记住本章

**上下文工程 = 提示工程的升级版**：提示工程只管"怎么写好这段话"，上下文工程管"模型这一次总共能看到哪些 token"——包括系统提示、工具定义、检索结果、对话历史、笔记，全都要在预算内挑选、排序、压缩。

---

## 1. 什么是上下文工程（9.1）

"上下文"就是**采样时那组 tokens**。工程目标只有一句：在这些 token 的效用上下注，稳定拿到期望结果。

| 对比项 | 提示工程 | 上下文工程 |
|---|---|---|
| 关注对象 | 提示词怎么写、怎么组织 | 进入上下文窗口的**一切**信息 |
| 工作时间 | 开发时设计一次 | 推理阶段每次调用都要策划 |
| 核心问题 | 怎么写出有效提示 | 从不断膨胀的"候选信息宇宙"里挑哪些进窗口 |
| 关系 | — | 提示工程的自然演进，是它的子集 |

关键在于：循环运行的 Agent 会不断产生下一轮可能相关的数据，这些信息**必须被周期性提炼**。不提炼就会淹掉真正重要的内容。

---

## 2. 为什么重要：上下文腐蚀（9.2）

### 2.1 上下文是稀缺资源

针堆找针（needle-in-a-haystack）基准揭示了一个反直觉现象——**上下文腐蚀（context rot）**：

> 上下文窗口里的 token 越多，模型准确回忆信息的能力反而下降。

这不是个别模型的 bug，几乎所有模型都有，只是退化曲线平滑程度不同。根本原因在 Transformer 架构：注意力的理论复杂度是 O(n²)，序列一长，模型对两两关系的建模能力就被"拉薄"；而且训练数据里短序列远多于长序列，模型对"全上下文依赖"的经验本来就少。

所以：**上下文有边际收益递减，模型有一笔"注意力预算"**。

### 2.2 有效上下文的"解剖学"（9.2.1）

用尽可能少、但高信号密度的 token，最大化拿到期望结果的概率。四个组件：

| 组件 | 要点 | 常见失败模式 |
|---|---|---|
| **系统提示** | 分区组织（角色/任务/工具指引/输出描述），用 XML 或 Markdown 分隔；追求「最小必要信息集」（最小 ≠ 最短） | ①过度硬编码：塞复杂脆弱的 if-else；②过于空泛：只给宏观目标，没有具体信号 |
| **工具** | 职责单一、低重叠、接口语义清晰、对错误鲁棒 | 「臃肿工具集」——边界模糊到人类工程师都说不准该用哪个 |
| **示例（Few-shot）** | 精挑多样且典型的示例，直接画像期望行为 | 把所有边界条件一股脑塞进去 |
| **动态检索** | 运行时按需加载，而非一次性全塞 | 预加载一堆用不上的数据 |

一句指导思想：**信息充分但紧致**。

### 2.3 从"预检索"到 JIT 上下文（9.2.2）

工程实践正在从「推理前一次性 embedding 检索」转向「**即时（Just-in-time）上下文**」：

- 不在启动时加载所有数据，而是维护**轻量化引用**（文件路径、查询语句、URL）
- 运行时通过工具动态加载所需内容
- 用 `head` / `tail` 只看看大文件的关键片段，而不是整块读进来

这个认知模式和人类一致：我们不背下所有信息，而是靠文件系统、收件箱、书签按需提取。

**元数据本身也在传递信息**：目录层级、命名约定、时间戳都在暗示"目的与时效"。`tests/test_utils.py` 和 `src/core/test_utils.py` 的语义暗示完全不同。

还有个好听的名字叫**渐进式披露（progressive disclosure）**：每步交互都产生新上下文，反过来指导下一步决策——文件大小暗示复杂度，命名暗示用途，时间戳暗示相关性。

代价：运行时探索比预计算检索慢，而且需要"有主见"的工程设计（正确的工具 + 启发式），否则 Agent 会误用工具、追死胡同。

**实用建议**：混合策略通常最优——前置加载少量高价值上下文保证速度，其余交给 Agent 自主探索（比如先给 README + `glob`/`grep` 原语）。

### 2.4 长时程任务的三大策略（9.2.3）

当任务超过上下文窗口（大型代码库迁移、跨小时的研究），光靠加大窗口解决不了，需要三个手段：

| 策略 | 定义 | 适用场景 | 关键做法 |
|---|---|---|---|
| **压缩整合（Compaction）** | 接近上限时做高保真总结，用摘要重启新窗口 | 需要长对话连续性 | 保留架构决策、未解决缺陷、实现细节，丢弃重复工具输出；先优化召回，再优化精确度 |
| **结构化笔记（Structured note-taking）** | 定期把关键信息写入上下文外的持久存储，后续按需拉回 | 有里程碑/阶段成果的迭代开发 | 维护 TODO 列表、NOTES.md、阻塞项索引；跨数十次工具调用仍保持进度一致 |
| **子代理架构（Sub-agent）** | 主代理做高层规划，子代理在"干净上下文窗口"里各自深挖，只回传 1000~2000 token 摘要 | 复杂研究/分析，可并行探索 | 关注点分离，庞杂搜索上下文留在子代理内部 |

经验法则：**要长对话连续 → 压缩；有阶段成果 → 记笔记；要并行深挖 → 子代理**。

## 3. ContextBuilder：GSSC 流水线（9.3）

HelloAgents 的上下文构建器，核心是一条四阶段流水线：**Gather（汇集）→ Select（选择）→ Structure（结构化）→ Compress（压缩）**。

### 3.1 设计目标（9.3.1）

| 目标 | 做法 |
|---|---|
| **统一入口** | 把 GSSC 抽象成可复用流水线，Agent 里不再重复写上下文管理代码 |
| **稳定形态** | 输出固定骨架，便于调试、A/B 测试、评估 |
| **预算守护** | token 预算内尽量保留高价值信息，超限有兜底压缩 |
| **最小规则** | 不引入来源/优先级等分类维度，只用「相关性 + 新近性」两维评分 |

固定的上下文骨架（这是本章最值得记住的模板）：

```
[Role & Policies]   Agent 角色定位和行为准则
[Task]              当前要完成的具体任务
[State]             Agent 当前状态和上下文信息
[Evidence]          从外部知识库检索的证据
[Context]           历史对话和相关记忆
[Output]            期望的输出格式和要求
```

### 3.2 两个核心数据结构（9.3.2）

**ContextPacket**——候选信息的最小单元：

```python
@dataclass
class ContextPacket:
    content: str                    # 信息内容
    timestamp: datetime             # 时间戳（算新近性）
    token_count: int                # token 数量（算预算）
    relevance_score: float = 0.5    # 相关性 0.0-1.0
    metadata: Optional[Dict] = None # 类型/来源等标记
```

**ContextConfig**——配置（默认值很能说明设计取舍）：

```python
max_tokens: int = 3000          # 总预算
reserve_ratio: float = 0.2      # 给系统指令预留 20%
min_relevance: float = 0.1      # 相关性下限
enable_compression: bool = True # 超限是否压缩
recency_weight: float = 0.3     # 新近性权重
relevance_weight: float = 0.7   # 相关性权重（两者之和必须为 1）
```

`reserve_ratio` 这个设计很关键——保证系统指令永远有位置，不会被检索结果挤掉。

### 3.3 GSSC 四阶段详解（9.3.3）

**① Gather：多源汇集，容错优先**

按顺序收集：系统指令（`relevance_score=1.0`，不参与评分）→ 记忆系统检索（limit 10，min_importance 0.3）→ RAG 检索（limit 5，min_score 0.3）→ 最近 5 条对话历史（基础分 0.6）→ 自定义 packet。

每个外部数据源都包 `try/except`——**单源失败不影响整体流水线**。这是生产级代码和教学代码最明显的区别。

**② Select：评分 + 贪心填充**

```python
combined_score = relevance_weight × relevance + recency_weight × recency
```

- 相关性：Jaccard 相似度（生产环境换成向量相似度）
- 新近性：指数衰减 `exp(-0.1 × age_hours / 24)`，24 小时内保持高分

然后**按分数降序贪心填充**，直到 token 预算用完。系统指令先扣，其余按分数塞。

**③ Structure：分区组装**

按 `metadata.type` 分到 `[Role & Policies]` / `[Evidence]` / `[Context]`，再拼 `[Task]` 和 `[Output]`。好处是可读、可调试（一眼看出哪个区有问题）、可扩展（加新信息源就是加新分区）。

**④ Compress：分区截断兜底**

超限时按 `\n\n` 切分区，逐个塞进预算，最后一个允许部分保留（至少留 50 token），末尾加 `[... 内容已压缩 ...]`。原则是**保持结构完整性**——宁可每区都短一点，也不要只剩前两个区。

> token 计数用的是朴素估算：中文 1 字符 ≈ 1 token，英文 1 词 ≈ 1.3 token。生产环境应换真正的 tokenizer。

### 3.4 集成到 Agent（9.3.4）

```python
class ContextAwareAgent(SimpleAgent):
    def run(self, user_input: str) -> str:
        # ① 构建优化上下文（自动汇集记忆 + RAG + 历史）
        context = self.context_builder.build(
            user_query=user_input,
            conversation_history=self.conversation_history,
            system_instructions=self.system_prompt,
        )
        # ② 用优化后的上下文调 LLM
        response = self.llm.invoke([
            {"role": "system", "content": context},
            {"role": "user", "content": user_input},
        ])
        # ③ 更新历史 ④ 把重要交互写进记忆
        return response
```

ContextBuilder 就成了 Agent 的"上下文管理大脑"。

## 4. NoteTool：结构化笔记（9.4）

### 4.1 为什么还要 NoteTool（9.4.1）

MemoryTool 管的是**对话式记忆**（工作/情景/语义），但项目式任务需要更轻、更人类友好的东西：

| 能力 | 说明 |
|---|---|
| 结构化记录 | Markdown + YAML 前置元数据，机器能解析、人能读能改 |
| 版本友好 | 纯文本，天然支持 Git |
| 低开销 | 不碰数据库，适合轻量状态追踪 |
| 灵活分类 | 用 `type` + `tags` 多维组织 |

### 4.2 存储格式（9.4.2）

每个笔记是一个 `.md` 文件，**文件名即 ID**：

```markdown
---
id: note_20250119_153000_0
title: 项目进展 - 第一阶段
type: task_state
tags: [refactoring, phase1, backend]
created_at: 2025-01-19T15:30:00
updated_at: 2025-01-19T15:30:00
---

## 完成情况
已完成数据模型层重构，测试覆盖率达到 85%。

## 下一步计划
1. 重构业务逻辑层
```

另有一个 `notes_index.json` 存所有元数据，用于**快速检索**和**完整性校验**（不用打开每个文件）。

### 4.3 七个核心操作（9.4.3）

| action | 作用 | 关键参数 |
|---|---|---|
| `create` | 新建笔记 | title, content, note_type, tags |
| `read` | 读取（解析 YAML + 正文） | note_id |
| `update` | 更新字段并刷新 `updated_at` | note_id + 任意字段 |
| `search` | 关键词搜标题和正文 | query, limit, note_type, tags |
| `list` | 按类型/标签列元数据 | note_type, tags, limit |
| `summary` | 统计（总数/类型分布/最近 5 条） | — |
| `delete` | 删文件 + 删索引 | note_id |

五种 `note_type` 各有语义，**建议按重要性用**：

```
blocker   （阻塞问题，优先级最高）
action    （下一步行动计划）
task_state（阶段性进展）
conclusion（重要结论）
reference （参考资料）
```

### 4.4 与 ContextBuilder 深度集成（9.4.4）

这是 NoteTool 真正的威力：

```python
def run(self, user_input: str) -> str:
    # ① 检索相关笔记（blocker 优先 + 关键词搜索，合并去重）
    notes = self._retrieve_relevant_notes(user_input)
    # ② 转成 ContextPacket（blocker 设 0.9 分，action 0.8，task_state 0.75，conclusion 0.7）
    packets = self._notes_to_packets(notes)
    # ③ 作为 custom_packets 注入上下文
    context = self.context_builder.build(..., custom_packets=packets)
```

于是 Agent 每轮对话都会**自动带上相关历史笔记**，回答能引用 `[笔记:重构项目-第一阶段]`。这个"按笔记类型设置不同相关性分数"的小技巧很实用。

## 5. TerminalTool：即时文件系统访问（9.5）

### 5.1 为什么需要（9.5.1）

**传统方式**：`rag_tool.add_document("./project/**/*.py")` —— 耗时、占存储、可能过时。
**TerminalTool 方式**：`find . -name '*.py'` → `grep -r 'class UserService' .` → `head -n 50 xxx.py` —— 快速、实时、按需。

典型场景：代码库探索、日志分析（`tail -n 100 app.log | grep ERROR`）、数据文件预览（`head -n 5 sales.csv`）。

这就是 9.2.2 节 JIT 上下文理念的落地。

### 5.2 四层安全机制（本节重点）

让 Agent 执行命令很强大也很危险，所以叠了四道防线：

| 层 | 机制 | 说明 |
|---|---|---|
| **第一层** | 命令白名单 | 只允许只读命令：`ls/cat/head/tail/grep/find/wc/sort/uniq/cut/awk/sed/pwd/cd/file/stat/du/df/echo/which` 等，`rm -rf /` 直接被拒 |
| **第二层** | 工作目录沙箱 | 用 `Path.relative_to(workspace)` 校验，`cat /etc/passwd`、`cd ../../../etc` 全部拒绝 |
| **第三层** | 超时控制 | 默认 30 秒，防死循环/资源耗尽 |
| **第四层** | 输出大小限制 | 默认 10MB，超出截断并提示 |

### 5.3 两个核心功能（9.5.2）

**命令执行**：`subprocess.run(shell=True, cwd=current_dir, capture_output=True, timeout=...)`，合并 stdout/stderr，非零返回码标警告，超时/异常都返回字符串而不是抛异常（保证 Agent 不崩）。

**目录导航**：`cd` 单独处理——支持 `..` / `.` / `~`，每次都做 `relative_to(workspace)` 校验，越界直接拒绝。这支持多步骤探索：

```
ls -la → cd src → find . -name '*service*.py' → cat user_service.py
```

### 5.4 与其他工具协同（9.5.4）

| 协同 | 做法 |
|---|---|
| + MemoryTool | `tree -L 2 src` 的结果存成语义记忆（importance 0.8） |
| + NoteTool | 日志里发现慢查询 → 自动创建 `blocker` 笔记 |
| + ContextBuilder | `ls -R src` 和 `git log --oneline -10` 转成 ContextPacket 注入上下文 |

## 6. 长程智能体实战：代码库维护助手（9.6）

### 6.1 场景与挑战

维护一个约 50 个 Python 文件的 Flask 应用，持续数天做重构。三个典型长程挑战和对应解法：

| 挑战 | 解法 |
|---|---|
| 代码量远超上下文窗口（数万行） | TerminalTool 即时按需探索，不预索引 |
| 跨会话状态管理（持续数天） | NoteTool 记录阶段进展、待办、决策 |
| 上下文质量与相关性（不被无关信息淹没） | ContextBuilder 智能筛选，保持高信号密度 |

### 6.2 三层架构

```
探索层  TerminalTool   ← 即时读代码
记忆层  NoteTool + MemoryTool  ← 跨会话状态
编排层  ContextBuilder ← 每轮挑最优上下文
```

### 6.3 核心实现：CodebaseMaintainer

**四种运行模式**（`mode` 参数决定预处理策略，很值得借鉴）：

| 模式 | 预处理动作 |
|---|---|
| `explore` | `find . -type f -name '*.py' \| head -n 20` 拿到结构 |
| `analyze` | `wc -l` 统计规模 + `grep -rn 'TODO\|FIXME'` 找待办 |
| `plan` | `note_tool.list(note_type="task_state")` 加载任务规划 |
| `auto` | 灵活决策 |

**`run()` 的六步骨架**：

```
① 按模式预处理 → 得到 ContextPacket
② 检索相关笔记（blocker 优先）→ 转 ContextPacket
③ ContextBuilder 构建上下文
④ 调 LLM
⑤ 后处理：回答里出现"问题/bug/错误/阻塞"→ 自动建 blocker 笔记
            用户提到"计划/下一步/任务"→ 自动建 action 笔记
⑥ 更新对话历史（超过 20 条裁掉旧的）
```

注意 ⑤ 这个**自动知识沉淀**设计——Agent 自己判断哪些内容值得记成笔记，不需要人提醒。

### 6.4 三天工作流的实际效果

| 阶段 | 发生什么 |
|---|---|
| 第一天·探索 | 摸清项目结构 → 发现 User.email 缺唯一约束等问题 → 自动建 blocker 笔记 |
| 第二天·分析 | 统计 3542 行、测试覆盖率仅 45%、12 个 TODO → 自动建多个 blocker；给出 `process_order` 的 8 层嵌套重构方案 |
| 第三天·规划 | 综合前两天所有笔记 → 输出高/中/低优先级任务表 → 更新 task_state 笔记 |
| 一周后 | `summary` 显示 8 条笔记（3 blocker / 2 action / 2 task_state / 1 conclusion），生成 JSON 报告 |

三个关键特性：**跨会话连贯**（第一天发现的问题第二天自动被考虑）、**智能上下文**（自动汇集相关笔记、按模式调整）、**自动知识管理**（发现即记录）。

## 7. 本章总结（9.7）

### 理论层

1. **上下文工程本质**：从提示工程演进而来，核心是管理有限的注意力预算
2. **上下文腐蚀**：长上下文必然带来性能下降，上下文是稀缺资源
3. **三大策略**：压缩整合、结构化笔记、子代理架构

### 工程层

| 组件 | 职责 |
|---|---|
| **ContextBuilder** | GSSC 流水线，统一上下文管理接口 |
| **NoteTool** | Markdown + YAML，结构化的长期记忆 |
| **TerminalTool** | 安全的命令行，即时文件系统访问 |
| **长程智能体** | 三者整合，跨会话的代码库维护助手 |

### 核心收获

- **分层设计**：即时访问（TerminalTool）+ 会话记忆（MemoryTool）+ 持久笔记（NoteTool）

## 附录：大白话理解

### 上下文工程到底在解决什么？

想象你要给一个**只有 7 秒记忆力但非常聪明的助手**交代一件复杂的事：

- **提示工程** = 琢磨怎么开口："请帮我……" vs "我需要你……"，哪句更容易让他听懂
- **上下文工程** = 决定**这次到底给他看哪些材料**：项目章程？昨天的会议纪要？那 300 页的技术文档？还是只给他一个文件路径让他自己翻？

后者才是真正的难题。因为助手再聪明，桌上堆 500 份文件他也会看花眼——这就是"上下文腐蚀"。

### 为什么塞得越多反而越差？

人的注意力有限，模型也是。Transformer 的注意力机制理论上要处理 n² 个两两关系，上下文一长，每个关系分到的"注意力"就被稀释。而且模型训练时见过的大多是短文本，长距离依赖的经验本来就少。

类比：**考试时给你一本 1000 页的参考书开卷，比给你 2 页精心整理的笔记，答题正确率可能更低**——因为找答案的时间成本、以及无关信息的干扰，都远高于那 2 页笔记。

### GSSC 四步 = 出门旅行前的打包流程

| 阶段 | 类比 |
|---|---|
| **Gather** | 把衣柜里所有可能穿的衣服都摊在床上（系统提示、记忆、RAG、历史、笔记） |
| **Select** | 按"这次去哪、天气如何"打分排序（相关性 × 新近性），箱子装不下就从低分的开始扔 |
| **Structure** | 分层收纳：外套一层、内衣一层、洗漱包一层（[Role]/[Task]/[Evidence]/[Context]/[Output]） |
| **Compress** | 实在装不下，就把毛巾卷小一点（分区截断），但保证每层都还有点东西（保持结构完整） |

`reserve_ratio = 0.2` 就像**先给护照和钱包留好位置**，剩下 80% 再装衣服——重要东西永远不会被挤掉。

### NoteTool 和 MemoryTool 有什么区别？

| 工具 | 类比 |
|---|---|
| **MemoryTool**（第八章） | **大脑的自动记忆**——你昨天聊过什么、对方喜欢什么，模糊但自动 |
| **NoteTool**（本章） | **桌上的项目笔记本**——你主动写下"第 1 阶段完成、第 2 阶段卡在依赖冲突"，条理清晰、可以翻页、可以给别人看 |

大脑记忆会淡、会混；笔记本不会。长项目靠笔记本，闲聊靠大脑。

而且笔记本用 Markdown + YAML，**用 Git 就能看版本变化**——"这条 blocker 是什么时候记的、什么时候解决的"，一目了然。这是数据库存储做不到的爽感。

### TerminalTool 为什么只让跑只读命令？

因为 Agent 有时候会"想当然"。你说"清理一下临时文件"，它可能真的执行 `rm -rf`。四层防护（白名单 + 沙箱 + 超时 + 输出限制）的本质是：**给老虎装上笼子再放出去干活**。

而且它的价值不只是安全——`grep` 一个关键词定位代码，比把整个代码库向量化再检索，**又快又准又不过时**。这就是"JIT 上下文"的威力：**要用的时候再去拿，而不是提前把所有东西背下来**。

### 为什么说这一章是"生产级 Agent 的分水岭"？

前面八章解决的是"Agent 能不能做对一件事"；这一章解决的是"Agent 能不能连续几天、几十轮、几万 token 之后还做得对"。后者才是真实业务的样子。

三个工具的分工特别能说明问题：

```
TerminalTool  →  眼前要用什么，立刻去拿（秒级）
MemoryTool    →  之前聊过什么，模糊记得（会话级）
NoteTool      →  项目做到哪一步了，白纸黑字（周/月级）
ContextBuilder → 这一轮该看哪些，精挑细选（每次调用级）
```

**四种记忆粒度，四个时间尺度**——这就是长程智能体和"玩具 Demo"的本质差距。
