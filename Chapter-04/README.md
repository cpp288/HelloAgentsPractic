# 第四章　智能体经典范式构建

> 本章是从「懂原理」到「会造」的转折点：不借助 LangChain 等框架，**从零手写**三种经典智能体范式。手写的意义不是重复造轮子，而是掌握框架替你处理了什么——输出格式解析、工具调用重试、防死循环——从而从「使用者」变成「创造者」。

## 0. 三种范式一句话对比

| 范式 | 一句话 | 类比 | 最适合 |
|---|---|---|---|
| **ReAct** | 边想边做，走一步看一步 | 侦探按线索推进 | 需要外部工具/实时信息、路径不确定 |
| **Plan-and-Solve** | 先列完整计划，再严格照做 | 建筑师先画蓝图再施工 | 逻辑路径确定、可分解的多步推理 |
| **Reflection** | 做完再自我审查并迭代改进 | 写完稿再校对 | 对质量/准确性要求高、可容忍延迟 |

**共性**：三者都在「一个循环 + 精心设计的提示词 + 输出解析」上做文章，差别只在**思考与行动如何组织**。

## 1. 环境准备与基础组件（所有范式的共用底座）

### 1.1 依赖与配置
```bash
pip install openai python-dotenv
```
`.env` 中统一放模型配置三件套（第四章在此基础上再加工具密钥）：
```
LLM_API_KEY="..."      # 密钥
LLM_MODEL_ID="..."     # 模型ID
LLM_BASE_URL="..."     # 服务地址（兼容 OpenAI 接口即可）
SERPAPI_API_KEY="..."  # ReAct 用的搜索工具密钥
```

### 1.2 `HelloAgentsLLM`：LLM 客户端封装
职责：把「调模型」这件事收敛到一个类里，主逻辑只管智能体本身。

- `__init__`：优先用传入参数，否则从环境变量读 `LLM_MODEL_ID / LLM_API_KEY / LLM_BASE_URL`；三者缺一就 `raise ValueError`；内部创建 `OpenAI(api_key, base_url, timeout)`。
- `think(messages, temperature=0) -> str`：调用 `chat.completions.create(..., stream=True)`，**流式**逐块拼接 `chunk.choices[0].delta.content`，边打印边收集，最后返回完整字符串。
- 关键细节：`if not chunk.choices: continue`（流式块可能没有 choices）；`temperature=0` 保证输出确定性；异常时返回 `None` 而不是抛出去。

> 这就是第一章 `llm_client.py` 的升级版，多了流式和默认参数兜底。

### 1.3 工具（Tools）：智能体的「手和脚」
一个好工具必须有三要素：
1. **名称（Name）**：简洁唯一，供 `Action` 中调用，如 `Search`
2. **描述（Description）**：**最关键**——LLM 完全靠这段自然语言判断「什么时候该用哪个工具」
3. **执行逻辑**：真正干活的函数

`ToolExecutor` 类（工具箱管理器）：
- `registerTool(name, description, func)`：注册，存成 `{name: {description, func}}`
- `getTool(name)`：按名取函数
- `getAvailableTools()`：把所有工具格式化成 `- 名称: 描述` 的多行文本，**直接塞进提示词**

## 2. ReAct（Reason + Act）

**核心思想**：把推理和行动显式交织，每一步输出固定三段式，形成 `Thought → Action → Observation` 循环。

### 2.1 为什么需要它
- 纯思考（CoT）：会推理但接触不到外部世界，事实容易幻觉
- 纯行动：直接输出动作，但缺乏规划与纠错
- ReAct：思考指导行动，行动结果反过来修正思考

### 2.2 提示词模板（机制的基石）
```
可用工具: {tools}
请严格按以下格式回应:
Thought: 分析问题、拆解任务、规划下一步
Action: 三选一
  - `{{tool_name}}[{{tool_input}}]`   调用工具
  - `Finish[最终答案]`               认为已得到答案
Question: {question}
History: {history}
```
要点：角色设定 + 工具清单 + **格式规约（最重要，让输出可被代码解析）** + 动态上下文（问题 + 累积历史）。

### 2.3 核心循环 `ReActAgent.run(question)`
```
while step < max_steps:
    1. 格式化提示词（tools + question + history）
    2. 调 LLM 拿 response_text
    3. 解析出 thought / action
    4. 若是 Finish[...] → 提取最终答案，return
       否则取工具名+入参 → 执行工具 → 得到 observation
    5. 把 "Action: ..." 和 "Observation: ..." 追加到 history
```
`max_steps` 是**安全阀**，防止无限循环烧钱。

### 2.4 两个解析器（最容易踩坑的地方）
- `_parse_output(text)`：正则分别抓 `Thought:` 之后、`Action:` 之后的内容（`re.DOTALL` 让 `.` 跨行）
- `_parse_action(action_text)`：正则 `(\w+)\[(.*)\]` 拆出「工具名」和「工具输入」

> 这部分正是教材在习题里让你反思的脆弱点：模型输出格式稍变（引号、嵌套括号、多余换行）就解析失败。更稳的做法是让模型输出 JSON。

### 2.5 特点与局限
- 优点：**高可解释**（Thought 链能看到心路历程）、**动态纠错**（可换搜索词重试）、**工具协同**（LLM 运筹 + 工具执行）
- 局限：强依赖 LLM 能力（格式/推理不行就断）、**串行多轮调用导致慢且贵**、提示词脆弱、缺乏全局规划易陷入局部最优/原地打转
- 调试四板斧：打印完整提示词 → 打印 LLM 原始输出 → 校验工具入参/返回格式 → 加 few-shot 示例 / 换模型

## 3. Plan-and-Solve

**核心思想**：任务明确拆成**规划（Plan）**与**执行（Solve）**两个阶段，先谋后动。

### 3.1 两阶段流程
1. **规划**：`P = π_plan(q)`，把问题分解成有序的 n 个步骤
2. **执行**：`s_i = π_solve(q, P, s_1..s_{i-1})`，逐步求解，每步都能看到「原问题 + 完整计划 + 历史结果」
3. 最终答案 = 最后一步结果 `s_n`

解决的是 CoT「多步骤长链条容易偏离轨道」的问题。

### 3.2 `Planner`：只负责做计划
提示词要点：**角色（顶级 AI 规划专家）+ 要求每步独立可执行且有序 + 强制输出 Python 列表 + 用 ```python 代码块包裹**。

解析选择用 `ast.literal_eval`（安全地把字符串变成 list），比正则解析自然语言稳得多；解析失败返回 `[]`，由上层判断终止。

### 3.3 `Executor`：执行 + 状态管理
执行器提示词必须包含四块信息：
- `{question}` 原始问题（别忘最终目标）
- `{plan}` 完整计划（知道当前步骤的位置）
- `{history}` 历史步骤与结果（当前步的直接输入）
- `{current_step}` 当前要解决的步骤
并要求「只输出该步答案，不要多余解释」。

**状态管理是灵魂**：每步结束把 `步骤 i: xxx / 结果: yyy` 累加进 `history`，下一步才能正确复用（如算周二时要用周一的 15）。

### 3.4 `PlanAndSolveAgent`：协调者
只做编排：`plan = planner.plan(q)` → 空则终止 → `executor.execute(q, plan)`。体现「组合优于继承」。

### 3.5 优缺点
- 优：结构性强、目标一致性好、逻辑稳定
- 劣：计划是**静态的**，执行中发现问题不会自动重规划（教材习题让你设计「动态重规划」/「分层规划」）

## 4. Reflection

**核心思想**：给智能体加一个**事后自省回路**——`执行 → 反思 → 优化`，反复迭代。

### 4.1 三步循环
1. **执行**：用 ReAct / Plan-and-Solve 等方式产出「初稿」`O_i`
2. **反思**：让模型扮演「评审员」，从事实错误 / 逻辑漏洞 / 效率 / 遗漏等维度挑错，产出反馈 `F_i = π_reflect(Task, O_i)`
3. **优化**：把初稿 + 反馈作为上下文，产出修订稿 `O_{i+1} = π_refine(Task, O_i, F_i)`
4. 循环直到「无需改进」或达到最大迭代次数

价值：内部纠错回路（不依赖外部工具反馈）、把一次性执行变成持续优化、轨迹本身构成「短期记忆」。

### 4.2 `Memory`：迭代的前提
没有记忆就无法迭代。极简实现：
- `records: List[{type, content}]`，type 取 `execution` / `reflection`
- `add_record(type, content)`：追加
- `get_trajectory()`：格式化成连贯文本，供提示词使用
- `get_last_execution()`：倒序找最近一次代码（作为反思对象）

### 4.3 三个角色提示词
| 提示词 | 角色 | 关键约束 |
|---|---|---|
| `INITIAL_PROMPT` | 资深 Python 程序员 | 完整签名 + 文档字符串 + PEP8，只输出代码 |
| `REFLECT_PROMPT` | **极其严格的代码评审专家** | 只盯算法效率，要求分析时间复杂度并提出更优算法；已最优才回答「无需改进」 |
| `REFINE_PROMPT` | 程序员（根据反馈改） | 输入原任务 + 上次代码 + 反馈，输出优化版 |

**角色设定的强度直接决定反思质量**——「极其严格」「对性能有极致要求」是刻意写的。

### 4.4 主循环 `ReflectionAgent.run(task)`
1. 初始执行 → `add_record("execution", code)`
2. `for i in range(max_iterations)`：
   - 取最近代码 → 反思 → `add_record("reflection", feedback)`
   - **若反馈含「无需改进」→ break**（终止条件）
   - 否则优化 → `add_record("execution", refined_code)`
3. 返回最后一次 execution

### 4.5 成本收益（重要判断）
- **成本**：每轮至少多 2 次模型调用（贵）、串行导致延迟高、提示词工程复杂度上升
- **收益**：方案质量阶梯式跃迁（功能正确 → 性能最优）、鲁棒性/可靠性提升
- 结论：**以成本换质量**。适合关键代码/技术报告/科研推演；实时性要求高或「大致正确就行」的场景，用 ReAct / Plan-and-Solve 更划算。

## 5. 三者怎么选
| 判断依据 | 选它 |
|---|---|
| 需要查外部信息、路径不确定、要动态纠错 | **ReAct** |
| 任务可清晰分解、逻辑链确定、要稳定 | **Plan-and-Solve** |
| 质量要求极高、能等、允许多次调用 | **Reflection** |
| 复杂现实任务 | **组合**：ReAct 拿信息 → Plan 拆步骤 → Reflection 审最终产出 |

---

## 6. 本章关键收获
- 智能体的骨架其实很朴素：**一个循环 + 一段强约束提示词 + 一个输出解析器 + 一个状态容器（history/memory）**。
- 三种范式的差异只在「思考与行动的组织方式」：交织（ReAct）、分离（Plan-and-Solve）、事后修正（Reflection）。
- 真正难的不是调模型，而是**工程细节**：格式解析的鲁棒性、死循环防护、工具描述的可读性、上下文的累积方式。
- 「先手写再上框架」的价值：知道框架帮你做了什么，才有能力在框架不够用时自己造。

## 附录：大白话理解第四章

> 这一章的所有代码，其实都在回答同一个问题：**怎么让大模型"干完一件事"？** 答案是把四样东西拼起来。

### 一个通用骨架：全家桶就这四样

| 零件 | 干什么 | 生活比喻 |
|---|---|---|
| 循环 | 反复"想一步、做一步" | 做事要一轮一轮推进 |
| 提示词 | 规定它怎么想、怎么输出 | 给员工的工作手册 |
| 解析器 | 把模型说的话翻译成代码能执行的动作 | 把口语翻译成操作指令 |
| 记忆（history/memory） | 记住做过的每一步 | 记事本，防止转头就忘 |

**三种范式的差别，只是这四样东西的摆放方式不同。** 就像同样是灶台、食材、锅，炒、炖、蒸出来的菜不一样。

### ① ReAct：像侦探破案
侦探不会一开始就知道凶手，他**走一步、看一步**：现场有什么线索（Thought）→ 去查这个线索（Action）→ 查到什么（Observation）→ 再决定下一步。
- 好处：能随机应变，查错了能换个方向再查。
- 坏处：走得慢、容易瞎转悠（所以要设 `max_steps` 上限）。

**你踩的那个 bug 特别有代表性**：侦探最后说"我找到答案了（Finish）"，但这句话是分两行说的，你的翻译官（正则）只认一行，于是崩溃了。所以要给翻译官留点余地。

### ② Plan-and-Solve：像装修队
装修队不会边砸墙边想布局，而是**先出一张完整图纸，再照着图纸一项项施工**。
- 好处：有条理、不容易跑偏、每步都能接着说上一句（今天刷完墙，明天铺地板）。
- 坏处：图纸是一次性画好的，施工中发现水管不对也得硬着头皮做下去（所以教材留了"动态重规划"的作业）。

### ③ Reflection：像写作文
写作文的做法是：**先写初稿 → 自己当老师批改 → 照着批注改**，改到自己挑不出毛病为止。
- 好处：第一版能交差，第二版才是好文章。
- 坏处：每多改一轮都要多花时间和钱，所以适合"质量比速度重要"的事。

### 为什么非要手写一遍？
因为框架会替你做好这三件脏活：**解析模型输出、重试失败的工具调用、防止死循环**。你不手写一遍，就只会在报错时干瞪眼——这正是你这次删 bug 花了最多时间的地方。

### 一句话记三章
> **ReAct 走一步看一步，Plan 先画图纸再干活，Reflection 写完再批改。三者共用一套骨架：循环 + 提示词 + 解析器 + 记忆。**
