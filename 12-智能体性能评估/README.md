# 第十二章　智能体性能评估

> 前面十一章把 Agent 造了出来、训了起来，但还差最后一步闭环：**怎么知道它到底好不好？** 换了模型、改了提示词，性能是涨了还是跌了？部署到生产前靠什么保证可靠性？这一章给 HelloAgents 加一套**评估系统**，用标准化基准 + 自动化指标把"感觉不错"变成"数字说话"。
>
> 框架版本：`pip install "hello-agents[evaluation]==0.2.7"`。GAIA 数据集需 HuggingFace 账号（`HF_TOKEN`）；BFCL 官方工具依赖 `numpy<=2.0.0`，需单独装 `pip install "numpy==1.26.4" bfcl-eval`。

---

## 0. 一句话记住本章

**没有评估的优化都是玄学**。评估 = 用统一的数据集、指标、评分方法，把 Agent 的能力量化成可比的数字，让每一次改动都有据可查。

---

## 1. 智能体评估基础（12.1）

### 1.1 为什么评估这么难

传统软件测试是「输入 → 断言输出」，Agent 不行，有三座大山：

| 挑战 | 说明 |
|---|---|
| **输出不确定** | 同一问题多个正确答案，不能简单对错 |
| **标准多样** | 工具调用查函数签名、问答查语义相似度，各有各的评法 |
| **成本高昂** | 每次评估大量 API 调用，动辄几百元 |

解决思路：学术界和工业界提出**标准化基准（Benchmark）**——统一数据集 + 指标 + 评分方法，让不同系统可比。

### 1.2 主流评估基准速览（教材分类）

| 类别 | 代表基准 | 评什么 |
|---|---|---|
| **工具调用** | **BFCL**（UC Berkeley，1120+ 样本，4 类别）、ToolBench（清华，16000+ 真实 API）、API-Bank（微软，53 个 API） | 理解意图→选工具→构造调用 |
| **通用能力** | **GAIA**（Meta+HF，466 题，3 难度级）、AgentBench（清华，8 领域）、WebArena（CMU，真实网页） | 多步推理 + 工具 + 文件 + 浏览 |
| **多智能体协作** | ChatEval、SOTOPIA、自定义协作场景 | 协同对话 / 社交互动 |

常用指标分四类：**准确性**（Accuracy / Exact Match / F1）、**效率**（响应时间 / Token 用量）、**鲁棒性**（错误率 / 故障恢复）、**协作**（通信效率 / 任务完成度）。

### 1.3 HelloAgents 的评估体系（三个场景）

| 场景 | 基准 | 选它的理由 |
|---|---|---|
| 工具调用能力 | **BFCL** | 数据量适中、指标清晰、社区活跃 |
| 通用助手能力 | **GAIA** | 任务真实、难度分级、综合性强 |
| 生成数据质量 | **AIME 数学题生成**（LLM Judge + Win Rate + 人工） | 完整体验"Agent 造数据→评数据"闭环 |

目录结构（三层：数据层 Dataset → 评估层 Evaluator → 指标层 Metrics，全部再封成 Tool）：

```
evaluation/benchmarks/
├── bfcl/      dataset / evaluator（AST 匹配）/ metrics / ast_matcher
├── gaia/      dataset / evaluator（准精确匹配）/ metrics / quasi_exact_match
└── data_generation/  dataset（AIME）/ llm_judge / win_rate
tools/builtin/
└── bfcl_evaluation_tool / gaia_evaluation_tool / llm_judge_tool / win_rate_tool
```

## 2. BFCL：工具调用能力评估（12.2）

### 2.1 四个评估类别（难度递增）

| 类别 | 测什么 |
|---|---|
| **Simple** | 单函数调用，最基础 |
| **Multiple** | 一次需要调多个函数 |
| **Parallel** | 并行调用多个函数 |
| **Irrelevance** | 判断**该不该**调函数（用户问题不需要工具时要忍住不调） |

### 2.2 核心算法：AST 匹配（不是字符串匹配）

把预测调用和标准答案都解析成**抽象语法树**再比，三个等价条件：

1. 函数名精确一致（`get_weather` ≠ `get_temperature`）
2. 参数键值对集合相等，**忽略顺序**（`f(a=1,b=2)` ≡ `f(b=2,a=1)`）
3. 参数值**语义等价**（`2+3` ≡ `5`、`"hello"` ≡ `'hello'`）

多函数场景：数量必须相同、每个都要匹配，但**调用顺序可不同**（集合匹配）。

指标：准确率、分类准确率、加权准确率、错误率。

### 2.3 官方工具

`bfcl evaluate --model-result-path ./results.json --test-category simple_python` —— 用官方 AST 算法，结果和排行榜一致，支持全部 BFCL v4 类别，自动生成报告。

## 3. GAIA：通用 AI 助手能力评估（12.3）

### 3.1 和 BFCL 的根本区别

BFCL 只看「函数调得对不对」；GAIA 看「**真实世界任务能不能做完**」——需要多步推理、知识运用、多模态理解、网页浏览、文件操作的综合运用。

数据集：**466 题**，分 **Level 1 / 2 / 3** 三个难度（零步推理 → 多步复杂推理）。每题带 `Annotator Metadata`（推理步骤、所需工具、耗时）。

### 3.2 核心算法：准精确匹配（Quasi Exact Match）

先**归一化**再精确匹配，归一化规则按答案类型分：

| 类型 | 归一化 | 示例 |
|---|---|---|
| 数字 | 去逗号、去单位符号 | `"$1,234.56"` → `"1234.56"` |
| 字符串 | 转小写、去冠词、去多余空格、去末尾标点 | `"The United States"` → `"united states"` |
| 列表 | 逗号分隔、逐元素归一化、按字母排序 | `"Paris, London, Berlin"` → `"berlin,london,paris"` |

这样 `"42"`、`"四十二"`（数字归一化后）、`"42.0"` 都能判对。

### 3.3 评估指标

- **精确匹配率**（核心）
- **分级准确率**：每个 Level 单独算
- **难度递进下降率**：`Drop Rate = (Acc_ℓ − Acc_ℓ+1) / Acc_ℓ`，衡量难度升高时性能掉多少（0 最理想）
- **平均推理步骤数**：答对的题平均用了几步

### 3.4 可提交官方排行榜

GAIA 支持把结果提交到 HuggingFace 官方排行榜，和全球模型对比。

## 4. 数据生成质量评估（12.4）

以 **AIME 风格数学题生成**为例，演示如何评估"Agent 造出来的数据"质量好不好。参考数据集 `TianHongZXY/aime-1983-2025`（900+ 真题，答案都是 0-999 整数，便于自动评估）。

三种互补方法，分工明确：

### 4.1 LLM Judge（绝对评分）

用强 LLM 当评委，从**四个维度**各打 1-5 分：

| 维度 | 评什么 |
|---|---|
| 正确性 | 题目和答案是否自洽、答案可解 |
| 清晰度 | 表述是否清楚无歧义 |
| 难度匹配 | 是否符合 AIME 难度（不是太简单也不超纲） |
| 完整性 | 条件是否充分、解答是否完整 |

汇总成三个指标：**平均分**（整体水平）、**及格率**（≥3.5 分占比，基本质量）、**优秀率**（≥4.5 分占比，高质量产出）。

优势：快、标准一致、还能给改进理由。

### 4.2 Win Rate（相对对比）

让 LLM 成对判断「生成题 vs 真题」哪个更好，统计 **Win / Loss / Tie** 比例，三者之和 = 100%。

**理想值 Win Rate ≈ 50%**：说明生成质量和真题旗鼓相当。远低于 50% → 不如真题；远高于 50% → 要么真超越了，要么评分标准有偏差。

### 4.3 人工验证

数学题要严格逻辑，自动化不够，必须人审。做了个 **Gradio Web 界面**：浏览题目→打分（正确性/清晰度/难度/完整性）→标状态（`approved` / `rejected` / `needs_revision`）→加评论。

> 为什么三种都要？LLM Judge 给绝对分、Win Rate 给相对差距、人工验证兜底严格正确性——**自动化提效 + 人工保质量**。

### 4.4 完整流程

生成题目 → LLM Judge 批量评分 → Win Rate 对比真题 → 人工抽检验证 → 生成综合评估报告。

## 5. 本章小结（12.5）

### 三层评估体系

| 层 | 评什么 | 算法 |
|---|---|---|
| BFCL | 工具调用准确性 | AST 匹配 |
| GAIA | 综合问题解决 | 准精确匹配 |
| AIME 生成 | 生成数据质量 | LLM Judge + Win Rate + 人工 |

### 六个核心技术要点

1. **模块化三层架构**：Dataset / Evaluator / Metrics
2. **工具化封装**：所有评估都封成 Tool，可被 Agent 调用、进工作流
3. **AST 匹配**：比字符串匹配智能（忽略顺序、识别等价表达式）
4. **多模态支持**：GAIA 支持文本 + 附件 + 图片
5. **LLM Judge**：多维自动评分 + 报告 + 可自定义维度
6. **Win Rate**：成对对比，接近 50% 即质量相当

### 四个扩展方向

加新基准（照 BFCL/GAIA 的 Dataset+Evaluator+Metrics 模式）→ 自定义指标 → 集成 CI/CD 防性能退化 → 扩展数据生成评估（更多数据类型、更多维度、多模型对比）。

## 6. 2025 → 2026：评估领域发生了什么（重要补充）

教材写于 2025 年上半年，基准和工具都在快速演进，几处关键更新：

### 6.1 GAIA 原版已接近饱和，GAIA-2 登场

教材用的 GAIA（466 题）在 2025 年被前沿模型快速刷高，**简单档已经饱和**（这是所有老基准的通病）。2026 年 2 月 **GAIA-2** 发布（arXiv 2602.11964），转向「**动态 + 异步环境**」——任务有时间敏感性、环境会随时间变化，更贴近真实 Agent 场景。结果：GPT-5（high）整体 pass@1 也只有 **42%**，说明长程动态任务远未解决。

→ 对本章实践：GAIA 原版仍可用于教学和快速回归，但想测真实能力上限，看 **GAIA-2**。

### 6.2 BFCL 已到 v4，工具调用能力接近天花板

BFCL 当前是 **v4**（截至 2026-11 排行榜 BTL-3 88.5%、Atria Dawn 77.0%、Qwen3.7 Max 75.0%）。随着模型工具调用能力快速提升，**简单/多函数调用已接近饱和**，前沿重心转向"带真实副作用的工具执行"和"长程工具链"。

→ 教材的 BFCL 四类别（simple/multiple/parallel/irrelevance）仍是基本功必测项，但别指望靠它拉开模型差距了。

### 6.3 基准"饱和"已成显学，出现饱和目录

2026 年有人专门维护「**Agent Benchmark Saturation Catalog**」（数据集版本 2026.09.3），跟踪哪些基准被刷爆、哪些还有区分度。选基准前先查这个，避免用一个已经饱和的基准得出"模型都差不多"的错误结论。

### 6.4 前沿基准格局（教材只覆盖了其中一小部分）

| 基准 | 评什么 | 2026 状态 |
|---|---|---|
| **SWE-bench / SWE-bench Verified** | 真实 GitHub issue 的代码修复 | 最主流的代码 Agent 基准；Verified 档 2026-09 领跑者 Claude Sonnet 4.5 ~76%、GPT-5.1 ~74% pass@1 |
| **GAIA-2** | 动态异步环境长程任务 | 2026-02 新出，GPT-5 仅 42% |
| **WebArena / VisualWebArena** | 真实网页交互 | 持续使用 |
| **τ-bench / TAU-bench**（Sierra） | 客服 Agent 的**政策遵循度** | 测"按规矩办事"，pass 率差距很大 |
| **OSWorld** | 操作系统级任务（GUI 操作） | 测电脑使用能力 |

教材的 BFCL + GAIA 覆盖了"工具调用 + 通用助手"，但**代码（SWE-bench）、客服（τ-bench）、电脑操作（OSWorld）** 这些 2026 年的热门方向教材没提。

### 6.5 评估工具生态爆发（EvalOps）

教材是自己手写评估器（Dataset/Evaluator/Metrics）。2026 年已经有成熟的"评估即平台"工具，不用从零造：

| 工具 | 定位 |
|---|---|
| **Promptfoo** | 开源提示词/模型评测，本地可跑，支持 LLM-as-judge |
| **LangSmith**（LangChain） | 评测 + 追踪 + 数据集管理一体化 |
| **OpenAI Evals** | OpenAI 官方评测框架 |
| **AgentOps / Athina / Galileo** | Agent 可观测性 + 评估，偏生产监控 |
| **Braintrust / Confident AI（deepeval）** | 开源评估 SDK |

→ 对本章实践：学习阶段自己实现一遍（理解 AST 匹配、准精确匹配这些算法本质，非常值得）；**生产环境直接用 Promptfoo 或 LangSmith**，别重复造轮子，它们还自带 CI 集成、防回归、报告生成。

### 6.6 LLM-as-Judge 的偏见被系统性研究

教材用 LLM Judge 评 AIME 题。2025-2026 大量研究指出 LLM Judge 有**位置偏见**（偏好先出现的答案）、**长度偏见**（偏好长答案）、**自我偏好**（偏好和自己风格像的答案）。缓解方法：成对比较时**随机化顺序**、用多个评委取多数、对评委也做校准。

→ 这正是教材习题 4 里"多评委评审团"的现实意义——单评委不可靠，陪审团更稳。

### 6.7 一句话总结这一节

教材教的是**评估的正确思维和最小实现**（三类基准 + 三种方法 + 三层架构），完全不过时；但**基准本身在快速饱和、工具生态在爆发、评委偏见被重视**。生产实践的建议是：**理解算法自己实现一遍打基础 → 然后用 Promptfoo/LangSmith 提效 → 选基准前查饱和目录 → LLM Judge 用陪审团防偏见**。

## 附录：大白话理解

### 评估到底在解决什么？

你改了 Agent 的提示词，感觉"回答好像更好了"。**感觉可靠吗？** 可能只是这次问题碰巧简单。评估就是把"感觉"变成"分数"——跑一套固定的题，看答对了几道，下次改完再跑同一套，分数涨了才是真的涨了。

类比：**考试**。没有统一考卷，你永远不知道学生是真进步还是这次蒙对了。

### 为什么 BFCL 用 AST 匹配，GAIA 用准精确匹配？

因为两者评的东西性质不同：

| | BFCL（工具调用） | GAIA（问答） |
|---|---|---|
| 答案形态 | 结构化的函数调用 `f(a=1, b=2)` | 自由文本 `"12847521"` 或 `"united states"` |
| 关键 | 调用语义对不对 | 答案意思对不对 |
| 难点 | 参数顺序无所谓、`2+3` 和 `5` 等价 | `"42"` / `"四十二"` / `"42.0"` 都算对 |

所以 BFCL 要**理解代码结构**（AST），GAIA 要**理解文本含义**（归一化 + 匹配）。如果拿字符串匹配评 BFCL，`f(a=1,b=2)` 和 `f(b=2,a=1)` 会被误判成错；如果拿 AST 评 GAIA，根本没法解析自然语言。

**工具选得对，才评得准**——这是本章反复强调的工程判断。

### 三种数据评估方法 = 三种"批改作业"方式

| 方法 | 类比 |
|---|---|
| **LLM Judge** | 老师按评分细则（4 个维度各 1-5 分）给每道题打绝对分，还写评语 |
| **Win Rate** | 把学生作文和范文放一起，让老师盲选"哪篇更好"，统计胜率 |
| **人工验证** | 教研组长亲自抽看，严格把关（机器看不懂的逻辑漏洞） |

为什么要三个一起用？因为：
- 绝对分（LLM Judge）**横向可比**，但尺度可能飘
- 相对胜率（Win Rate）**锚定真题**，告诉你"离标杆还有多远"
- 人工验证**兜底底线**，防止自动化漏判

理想状态：Win Rate ≈ 50%（学生作文和范文难分高下）。这是个很巧妙的设计——**不是追求 100% 胜率，而是追平标杆**，追平就说明质量到位了。

### 为什么"难度递进下降率"是个好指标？

光看总准确率会骗人。比如 Agent 总准确率 70%，可能是简单题全对、难题全错（偏科），也可能是各难度均衡（扎实）。

**Drop Rate** 就是看难度升高时掉多少：
- 从 Level 1 到 Level 2 掉 33% → 一加难度就崩
- 全程不掉 → 基本功扎实

类比：**考试不能只看总分，还要看"基础题 vs 压轴题"的得分分布**，才知道是真会还是只会简单的。

### 为什么评估成本高，还要搞分层？

跑一次 GAIA 全量可能花几百块 API 费。每次改一行提示词都跑全量，钱包受不了。所以教材习题里提到的**分层评估策略**很实用：

| 层 | 成本 | 用途 |
|---|---|---|
| 快速评估（小样本子集） | 几毛~几块 | 日常开发，改完就跑 |
| 标准评估（某类别全量） | 几十块 | 发版前 |
| 全面评估（全基准 + 多模型对比） | 几百块 | 重大更新 / 对外发布 |

**小钱天天花，大钱关键时候花**——这就是评估的成本艺术。

### 本章最值钱的一句话

「没有评估的优化都是玄学」。你在第四到十一章学的所有能力（推理、工具、记忆、上下文、协议、RL），**最终都要靠评估来证明它们真的让 Agent 变好了**。评估是整个 Agent 工程的**闭环收尾**，也是持续迭代的**指南针**。
